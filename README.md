# 《字界远征》— EG4S20 上的字符 RPG（HDMI 直出，可接显示屏玩）

把之前那个网页版 RPG 搬进 FPGA：**没有 CPU、没有软核、没有 SDRAM**，  
全部逻辑在 EG4S20 里用组合/时序电路实现，HDMI 直接输出 640×480p60 的画面，  
用板载 4 个按键玩。

---

## 一、和网页版的关系

|              | 网页版          | FPGA 版                               |
| ------------ | ------------ | ------------------------------------ |
| 渲染           | DOM + CSS    | 40×30 字符屏，16×16 点阵，BRAM 存格子          |
| 游戏逻辑         | JavaScript   | 状态机（`rpg_core.v`）                    |
| 内容（文案/怪物/数值） | JS 对象        | **`tools/build_rom.py`** 里的 Python 表 |
| 存档           | localStorage | 无（断电重来，字符游戏的常规做法）                    |

数值完全沿用网页版：3 职业、5 区域、15 种怪物、同样的伤害公式和成长曲线。

---

## 二、架构

```
 按键 x4 ──► key_debounce ──►┌──────────────┐
                             │  rpg_core    │  游戏状态机 + 指令解释器
                             │  (纯 Verilog)│
                             └──┬───────────┘
                                │ 写格子 {bg,fg,glyph} 16bit
                                ▼
                          ┌──────────────┐        ┌──────────┐
                          │  rpg_video   │◄───────┤ font_rom │ 16x16 点阵
                          │ 40x30 字符屏 │        └──────────┘
                          └──┬───────────┘             ▲
                             │ rgb565                │
                             ▼                       │
                          ┌──────────────┐      ┌────┴─────┐
                          │   hdmi_tx    │◄─────┤ cmd/str/ │ 界面指令 + 文字
                          │ TMDS 编码    │      │ art ROM  │ + 精灵
                          └──┬───────────┘      └──────────┘
                             ▼
                      HDMI 3 数据对 + 1 时钟对
```

**为什么不需要 SDRAM**：一屏只有 40×30 = 1200 个格子，每个 16bit，共 2.4KB。  
整屏塞进 BRAM 就够了，没有帧缓存、没有带宽问题、也没有读写撕裂风险——  
这是字符游戏相比图片播放器最大的优势。

## 三、屏幕规格

| 项    | 值                                               |
| ---- | ----------------------------------------------- |
| 分辨率  | 640×480 @60Hz（CEA-861 480p）                     |
| 像素时钟 | 25.175 MHz                                      |
| 字符网格 | 40 列 × 30 行                                     |
| 每格   | 16×16 像素，16bit = {bg[3:0], fg[3:0], glyph[7:0]} |
| 字库   | 252 个字形（ASCII + 中文 + 自绘边框图元）                    |
| 调色板  | 16 色（RGB565）                                    |

**为什么 ASCII 要水平放大一倍**：中文是 16×16 满格，ASCII 用系统字体只有 8 宽。  
不放大就会出现"H P   1 2 0"这种拉开的字距，所以 ASCII 在生成字库时就横向加倍了。

**边框不用系统字体的制表符**：实测宋体 16px 下 `┌─│` 只画了四分之一格，  
拼出来的框是断的。所以边框是 `build_rom.py` 里用像素画出来的图元（`_tile()`）。

## 五、改内容不用碰 Verilog

所有文案、怪物数值、精灵图、界面排版都在 `tools/build_rom.py` 顶部：

```python
ENEMIES = [("史莱姆", 36, 8, 2, 9, 7, 0, 0), ...]   # 名字,hp,atk,def,exp,gold,精灵,是否BOSS
AREAS   = [("新手村外", [0,1], 10), ...]            # 区域名, 两只小怪, 首领索引
SPRITES = {0: ["    ▓▓▓▓    ", ...]}                # 方块画的精灵，12x9
def screen_battle():                                 # 界面排版
    o += S(2, 1, "生命", GRAY)                       # S(x,y,文字,颜色)
```

改完跑一次：

```bash
python tools/build_rom.py
```

它会重新生成字库/指令表/精灵表，**同时把每个界面渲染成 `preview/*.png`**——  
不用上板就能看到排版对不对，这一步能省掉大量调试时间。

> 字形总数上限 255（0xFF 是字符串结束符）。超了脚本会直接报错并打印当前用到的  
> 所有汉字，照着删几个字就行。

## 五点五、跑仿真：装个 Icarus Verilog 就行

板子没到也能跑，用 **Icarus Verilog**（免费开源，Windows 有一键安装包）。
它跑的是**真实 RTL**，而且支持 `$fwrite`，所以测试台直接把画面存成文件，
不用再解析波形。

### 1. 下载安装

| 平台 | 地址 |
|---|---|
| Windows | http://bleyer.org/icarus/ → `iverilog-v12-x64_setup.exe` |
| macOS | `brew install icarus-verilog` |
| Ubuntu | `sudo apt install iverilog` |

Windows 安装时勾选 "Add to PATH"，装完开个新终端，`iverilog -V` 能出版本号即可。
顺手也装上 **GTKWave**（同一安装包里自带），后面想看波形用得上。

### 2. 跑

```bat
sim\iverilog\run.bat
```
（Linux/macOS：`./sim/iverilog/run.sh`）

它做三件事：编译 → 仿真 → 把像素转成 PNG。
输出在 `preview/sim/frame_01.png`、`frame_02.png`……**一张图对应一次按键**。

实测（Icarus Verilog 12.0，Windows）：编译零错误零警告，19 次按键耗时约 2 分半，
`frames.rgb` 17.5 MB。`preview/sim/` 里那 19 张图就是这么来的。

**务必在工程根目录跑**——RTL 里的 `$readmemh("rtl/gen/font.hex", …)` 是相对路径，
换目录会读不到字库（现象是满屏只有边框没有字）。

### 3. 自己玩

按键不能真敲（终端仿真器读不了键盘），改成读脚本 `sim/iverilog/keys.txt`，
一行一个键（1~4），按顺序生效：

```
1    标题页按 KEY1 -> 选职业
1    按 KEY1 选剑士 -> 地图
1    地图上 KEY1 = 探索，进入战斗
1    战斗里 KEY1 = 攻击
1    敌人死了就回地图，再按 KEY1 又是探索……
...
4    讨伐满 4 只后按 KEY4 挑战首领
```

**关键：一路按 1 就能自动打下去**——战斗里 KEY1 是攻击，地图上 KEY1 是探索，
敌人一死就自动回地图，所以连按 KEY1 会"打完一只→遇敌→继续打"。
示例脚本是 `1 1` + 16 个 `1` + `4`，正好打进第一个首领。

测试台会在**渲染器空闲时**自动按下一个键，所以不用算时序。
改完脚本重跑一遍就能看到每一屏；脚本越短跑得越快（一个键约 2 帧、两秒左右）。

### 4. 想看波形

测试台默认不导 VCD（太大了：一帧 42 万周期）。要看信号就把 `tb_play.v` 里
`dump_frame` 换成 `$dumpfile("wave.vcd"); $dumpvars;` 并把运行周期砍到几千，
再用 GTKWave 打开。

## 五点六、不想装东西？双击就能玩

`rpg_player.html` 是个单文件仿真器：**双击用浏览器打开就能玩**，键盘 1 2 3 4 操作，
右侧还能看到场景号、指令指针、寄存器值和指令流。

它跑的是**同一套 ROM**（`rtl/gen/*.hex` 原封不动打包进去）和**同一套状态机**，
已经和 Verilog 仿真做过逐格比对：

```
  title  @t=45000   差异 0 格  一致
  cls    @t=140000  差异 0 格  一致
  map    @t=240000  差异 0 格  一致
```

改完游戏内容后重新生成：

```bash
python tools/build_rom.py      # 先更新 ROM
python tools/build_player.py   # 再打包进 HTML
```

> 注意：HTML 版是"逐格一致"而不是"逐门电路一致"——它复刻的是解释器和状态机，
> 不是触发器。真正上板前的那道关，还是得靠 iverilog 跑真实 RTL。

## 五点七、我用来查 bug 的内部流程（可选）

下面这套是 yosys 的 WASM 版 + 自写 VCD 解析，不依赖任何本地工具链，
适合在没有 iverilog 的环境里做自动化回归：

| 脚本 | 作用 |
|---|---|
| `tools/run_sim.py` | 生成 ROM → 仿真 → 重建三屏 → 逐格比对（几秒）|
| `tools/run_sim.py --video` | 加上整帧像素验证（约 5 分钟）|
| `tools/vcd_screen.py` | VCD → 字符屏文本 |
| `tools/vcd_frame.py` | VCD → 640×480 PNG |
| `tools/frame_diff.py` | 与参考渲染器逐像素比对 + 搜最佳对齐 |
| `tools/check_player.js` | 验证 HTML 仿真器与 RTL 逐格一致 |

实测：

```
仿真帧点亮: 8810     参考帧点亮: 8794
最佳对齐 误差=0 dy=0 dx=-1
差异像素数: 0
```

### 这套流程实际抓到的 9 个 bug

| # | 现象 | 根因 |
|---|---|---|
| 1 | 第一屏被清屏两次，边框画成小框 | `FRAME` 宽高寄存器只有 4 位，40/30 被截成 8/14 |
| 2 | 取到的总是上一条指令 | 同步 ROM 输出要 2 拍，状态机只等了 1 拍（取指/取字/取精灵三处）|
| 3 | 一次按键连跳三四个界面 | 按键电平触发，长按会连续执行 |
| 4 | 金币超过 1023 显示成 176 | `num_rem` 只有 10 位 |
| 5 | 数字显示成乱码 | 数字用 ASCII `0x30+n`，但字库是自定义索引 |
| 6 | 进度条只画 1 格 | 指令里没编码宽度，RTL 硬编码 12 格 |
| 7 | 精灵 id 34 的插画串成史莱姆 | id 用 5 位装不下 34，基址也超 11 位 |
| 8 | 整屏文字被打散、只剩零碎笔画 | "提前一格预取"在行末跨行时子行号错拍，改成三级直流水线 |
| 9 | **iverilog 编译直接报错** | `font_a` 声明成 `reg` 却用 `assign` 驱动（yosys 只告警，iverilog 是硬错）|
| 10 | **战斗中按键完全没反应** | 按键处理写成 `else if (bst == B_IDLE)`，挂在 `if (scene == SC_BATTLE)` 的 else 上，战斗时永远进不去 |
| 11 | **战斗页整屏被刷成垃圾** | 消息字符串是在写出 `str.hex` **之后**才追加的，ROM 里根本没有，`MSG` 读到表尾越界数据，永远遇不到结束符 0xFF |

> 第 9 个特别值得记：**不同工具的严格程度不一样**。yosys 能过的代码 iverilog 未必能过，
> 上板前一定要用目标工具链编译一次。

### 经验

- VCD 每周期有 **2 个时间戳**，采样必须用 `clk` 上升沿，不能按信号变化数
- `we` 在清屏时常高，VCD 只记变化 → 按上升沿计数会漏掉 99% 的写
- 判断画面错在哪，最快的办法是和参考渲染器做**互相关**搜 dy/dx，误差不为 0 才继续查
- 长仿真别在 Git Bash 后台跑（父 shell 退出时子进程被回收），要前台 + 长超时
- **一定要"玩一遍"**：前 8 个 bug 仿真都测不出来，第 10 个（战斗按键）是连着按十几下才暴露的
- 资源表类的东西（字符串表、名字表）生成顺序很容易错——生成完要**回头核对长度和地址**

## 六、上板三件事

### 1. PLL（不改就没画面）

`rtl/clk_gen.v` 里打开注释，用 TD 的 IP Generator 生成：

- 输入 50MHz
- 输出 c0 = **25.175MHz**（像素时钟）
- 输出 c1 = **125.875MHz**（5× 像素时钟，给 TMDS）

配不出小数分频就退用 25.000/125.000，帧率变 59.5Hz，显示器照样认。

### 2. 引脚

`constraints/rpg_pins.adc` 里所有 `LOCATION` 都是占位值，按 HX4S20C 原理图改。  
**HDMI 必须落在支持 LVDS 的差分对上，P/N 同组**；TD 只约束 P 端。

### 3. hex 文件路径

四个 ROM 用 `$readmemh("rtl/gen/xxx.hex", mem)` 初始化。TD 的工作目录是工程根目录，  
所以要么保持这个相对路径，要么把 `rtl/gen` 加进搜索路径。  
**路径不对的表现是所有文字消失、只剩边框**——这是最快的排查信号。

### 4. TMDS 串行化

`tmds_serdes.v` 里 `USE_ODDR_PRIM` 没定义时是行为模型（只能仿真）。  
上板要接安路的 DDR 输出原语，或者直接用 TD 的 LVDS/SerDes IP 替换输出级。  
480p 时串行率只有 251.75Mbps，比 720p 好做得多。

## 七、怎么玩

| 界面    | 1   | 2    | 3  | 4        |
| ----- | --- | ---- | -- | -------- |
| 标题    | 开始  |      |    |          |
| 选职业   | 剑士  | 法师   | 游侠 |          |
| 地图    | 探索  | 商店   | 休息 | 首领/前往下一区 |
| 战斗    | 攻击  | 技能   | 药水 | 逃跑       |
| 商店    | 买药水 | 买大药水 | 强化 | 离开       |
| 死亡/通关 | 确认  |      |    |          |

流程：每区打 4 只小怪解锁首领 → 击败首领 → 按 4 进入下一区 → 5 区首领 = 通关。

**核心机制和网页版一样**：只用普攻打不动硬怪，必须在有蓝时用技能  
（剑士重斩无视 40% 护甲、法师火球无视 60%、游侠三连射）。

## 八、资源占用（估算）

| 资源   | 用量                                                    | EG4S20 占比 |
| ---- | ----------------------------------------------------- | --------- |
| BRAM | ≈167 Kb（font 65 + cmd 33 + str 16 + art 33 + cell 19） | ≈29%      |
| LUT  | ≈2500                                                 | ≈13%      |
| FF   | ≈1200                                                 | ≈6%       |
| PLL  | 1 / 4                                                 | —         |

比之前的 HDMI 播放器省得多——没有 SDRAM 控制器、没有 DDR 接口、没有跨时钟域。

## 九、已知限制

1. **没有存档断电丢失**——加存档要挂 Flash + 写保护逻辑，字符游戏没必要。
2. **只有 40 列**——中文 16px 一格，40 列约等于 DOS 的 40 列模式。  
   想要 80 列得把格子改成 8×16，中文占两格，那是另一套渲染逻辑。
3. **战斗只有普攻 + 一个技能**——4 个按键要覆盖所有界面，技能做了减法。
4. **没有动画**——受击/攻击没有特效，只有文字和血条变化。想加可以在  
   `rpg_video` 里做一个"整屏闪烁"的颜色叠加，成本很低。
5. **字库 252 字上限**——超了要改成 9bit 字码，格子变 17bit，改动不大但没必要。

## 十、如果这是给赛题用的

这个作品**不属于**赛题一（HDMI 多媒体播放系统）的功能要求，但可以作为一个  
"基于同一平台的独立扩展作品"，或者拆出两个可复用的技术点写进文档：

1. **字符屏渲染引擎**——40×30 字符、两级 BRAM 预取隐藏延迟、指令表驱动排版。  
   这套东西可以复用到任何需要文字叠加的场合（比如赛题里的 OSD 字幕）。
2. **无 CPU 的界面描述方法**——把 UI 从 Verilog 里挪到生成器脚本，  
   现场改界面不用重新综合逻辑，只换 ROM 内容。

如果要把字符屏塞回赛题的播放器做字幕层，`rpg_video` 可以直接当一个  
"文字图层"用：它输出 rgb565 + de/hs/vs，和原来的视频管线接口一致。
